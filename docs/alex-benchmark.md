# Alex 的成熟项目对标与交付标准

核验日期：2026-09-30。对象是个人外贸专家 Agent：用户交代生意和目标，Agent 研究真实客户、保存证据、处理沟通并续接任务。工程测试、真实账号验收和商业效果分别记录。

## 参考项目与采用的机制

| 参考 | 实际参考点 | Alex 的选择 |
| --- | --- | --- |
| [Hermes Agent](https://github.com/NousResearch/hermes-agent) | 同一 Agent 循环、profile 隔离、记忆和技能、Gateway、持久定时任务 | 继续使用 Hermes 内核、原生安装器和 scheduler，Alex 专注外贸身份、客户证据与沟通记录 |
| [Deep Agents](https://github.com/langchain-ai/deepagents) | 长任务的状态与上下文管理、持久化、人工介入、可评测执行 | 不引入第二个 Agent 框架；将关键业务停止条件、幂等和恢复写在工具及数据库中，用行为测试核验 |
| [Gmail 线程规范](https://developers.google.com/workspace/gmail/api/guides/threads) | threadId、RFC 回复头与主题匹配 | 回复使用已同步原邮件的真实 Message-ID 和线程，不用相同主题冒充线程回复 |

Hermes 本地源码审阅版本为 `db39ee3f2892185087bb2432eac242361056fc19`，包括 `cron/jobs.py`、`hermes_cli/cron.py`、`hermes_cli/subcommands/cron.py`、`hermes_cli/doctor.py` 与 Google Workspace 脚本。既有内核研究见 [Hermes 源码研究](alex-hermes-study.md)。Deep Agents 本轮对照公开架构和能力说明，没有将它的代码复制进 Alex。

## 审查结论

v0.3 已具有 Agent 运行基础，但距离可以长期委托仍有明显差距。主要缺口是客户回复没有进入持久业务状态、跟进只有提示词与泛用 cron、跨终端连接配置容易丢失，以及没有真实模型和账号的业务验收。图标和工具数量不能证明这些能力。

| 维度 | v0.3 观察到的问题 | v0.4 的改进 | 仍需满足的验收 |
| --- | --- | --- | --- |
| 自然对话与长期记忆 | 已接 Hermes，但没有真实模型完整对话记录 | 保持同一内核；启动时提示持久跟进日程，业务事实仍有来源 | 用户实际模型连续多轮、重启续聊、纠正过期业务事实 |
| 客户研究 | 有浏览器、证据和去重；生产客户数为 0 | 保留现有研究链路与真实性约束 | 三个真实研究任务、人工复核样本和联系信息证据覆盖率 |
| 客户沟通 | Gmail 可查读和发新邮件，缺少原线程回复 | 真实线程同步、消息 ID 去重、原线程回复、确切联系人绑定 | 用户控制邮箱的发送→回复→同步→答复实测 |
| 长期跟进 | 没有领域跟进日程，通用 cron 不能表达客户状态 | SQLite 跟进记录、时区、到期判断、回复/退订/取消停止、模糊回执不重发 | 真实回信、断网、重启、跨日额度与后台巡检联调 |
| 后台运行 | 可透传 Hermes cron，但需自己写任务 | 幂等安装原生跟进任务、专用技能、限定工具集、已有任务保持原配置 | 模型和邮箱配置完成，Gateway 常驻；核验原生 run history |
| 安装使用 | token 路径每个终端设置；状态检查不验证 API 凭据 | `connect` 保存路径，`doctor` 真正检查业务认证，`start` 管理本次服务生命周期 | 全新 Linux/WSL2 安装与干净 Windows 主机安装实测 |
| 工程可信度 | 已有确定性测试，但没有获客质量基线 | 回复/跟进行为回归、旧账本升级、真实 Hermes loader 和原生 cron 存储验证 | 固定人工标注评测集、真实来源故障案例、发布回归记录 |

## 本轮交付的业务闭环

1. Agent 基于真实客户证据准备内容，经用户本机策略允许后发送。
2. 用发送结果的 provider thread ID 同步线程，保存原始消息 ID、时间、正文摘要及截断标记。不会标记已读。
3. 用户要求跟进时保存原 deliveryId、带时区的到期时间和目的。重启之后仍从同一记录继续。
4. 到期发送前重新读取线程。读取失败时停止；客户已回信、用户取消或退订时停止；发送状态不确定时进入待复核。
5. 已同步的来信可用原 Message-ID 准备同线程答复，仍受确切收件人策略与额度控制。
6. 用户启用 Hermes 原生定时任务后，后台按相同工具和规则巡检。账号和模型未配置时，安装任务不会被报告为正在工作。

这是单个用户、单个 Alex profile 的 Gmail 跟进闭环。它不等于全渠道自动销售平台，也不证明已产生真实客户或营收。

## 分阶段验收

**个人 Agent 可用：** 用户提供产品、市场与买家类型；真实模型完成一次从资料了解、研究、证据复核到草稿交付；新会话不丢失事实，失败能解释具体阻塞。客户是否符合目标由实际证据及人工判断确认。

**后台可委托：** 用户指定收件人、额度、频率和停止条件。用户控制的邮箱收到邮件并回复；下次巡检读取真实回复且不发送原催发。关闭及重启 Gateway 后复查同一记录，不产生重复消息。记录检查前后收到的回复存在小时间窗口，无法保证在最后一次读取之后到达的回复能阻止已经提交的发送。

**可交付安装：** 在新的 Linux/WSL2 环境按文档安装，连接、模型、OAuth 与 Gateway 各有准确状态；更新保留账号、记忆与账本；备份恢复复现消息 ID 和停止状态。Windows 原生 Hermes + WSL2 业务服务是组合方案，不宣称 Windows 原生后端已经验证。

**获客质量：** 用不少于 50 条经人工标注的候选建立固定集合，记录目标匹配、来源可复查、邮箱出处、重复率和失败率。没有标注集前不公布模型准确率；测试网站和替身收件人不计为真实客户。

## 下一轮优先级

1. 在实际模型及用户控制账号上完成上述验收，修复真实失败；目前这仍是最高优先级。
2. 打通 WhatsApp 入站、消息回执和适用的 Cloud 模板流程，沿用客户身份与停止条件；当前只支持已有发送路径。
3. 增加可审计的发送结果对账，解决不确定结果由人工核查的问题。
4. 基于实际来源样本增加授权 Maps / 海关数据，再扩展行业技能和多语言匹配。
5. 有明确团队需求后再增加多租户、角色权限、在线服务和租户备份；当前不为此替换数据库或增加服务层。

## 可重复验证入口

```bash
npm test
npm run test:hermes
npm run test:legacy
# 使用已安装 Hermes 自带的 Python：
python integrations/hermes/verify_native.py
```

`test_followups.py` 覆盖回复停止、第三方/旧邮件不误判、旧库升级、原线程约束、收信失败不催发、时区、取消、退订、重启和快照。原生验证真实调用 Hermes 的 loader 与 cron 存储，在临时 profile 创建暂停任务并验证幂等，不调用模型、不访问真实邮箱、不发送消息。
